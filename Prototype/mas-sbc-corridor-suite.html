How this prototype works

Graph: the 84 stations MAS→SBC and 83 sections between them are built directly from the corridor datasets — real distances, platform counts and loop-line/junction complexity per station, and per-section train density and median scheduled running time computed from the timetable data.

Propagation: the datasets provided only contain scheduled times, not historical actual-vs-scheduled delay records, so there's no ground truth to train the GAT+GRU model described in the solution on yet. This prototype substitutes a hand-tuned propagation rule — carry-forward decay, a junction/train-density congestion bump, and schedule-slack recovery — over the same real graph, so the interaction (map, chaining, uncertainty, cross-train coupling) behaves the way the trained model is meant to. Swapping this rule for a trained GAT/GRU stack on real AVAS logs is the next step, not a redesign.

  • Delay chaining: each section's Δ builds on the last, discounted by recoverable timetable slack.
  • Congestion bump: stations with more platforms/loop lines and edges with more scheduled trains add extra Δ.
  • Uncertainty: grows with number of remaining sections and local junction complexity.
  • Network effect: a second train sharing an upcoming congested station absorbs a fraction of the same disruption.

The other five tabs above are operator/passenger-facing views built on the same graph and propagation rule, driven by a shared simulated clock and a list of injected congestion events (top bar) rather than this tab's single what-if control — that's the more "live corridor" way of using the same model.
